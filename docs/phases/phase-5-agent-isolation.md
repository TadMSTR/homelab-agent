# Phase 5 — Agent Isolation

**Completed:** 2026-04-03  
**Snapshots:** pre-Phase-5 and post-Phase-5  
**Smoke tests:** all passed

## What Was Built

Phase 5 hardened the agent runtime with full OS-level isolation: Unix user separation, AppArmor profiles in enforce mode, seccomp syscall filtering, and per-agent NATS credential files scoped to each Unix user. Agents now run as dedicated system users with no access to each other's home directories or credentials.

## Components Deployed

### Unix Agent Users

Three dedicated system users (no login shell, no sudo):

| User | Runs | Home |
|------|------|------|
| `helm-temporal` | temporal-worker agent | `/home/helm-temporal/` |
| `helm-platform` | platform agent | `/home/helm-platform/` |
| `helm-health` | platform-health check | `/home/helm-health/` |

Home dirs are `700` — helm-launch reads the NATS cred file from within each user's home using the sudoers entry. `/home/ted/` requires `o+x` to allow traverse by these users for any shared paths.

### AppArmor Profiles (Enforce Mode)

Four profiles generated from manifests and loaded into enforce mode:

| Profile | Agent |
|---------|-------|
| `helm-helm-build` | helm-build |
| `helm-platform` | platform |
| `helm-temporal-worker` | temporal-worker |
| `helm-platform-health` | platform-health |

Profiles are generated by `gen-apparmor-profile.py` from the manifest's `filesystem` declarations. Applied via `AppArmorProfile=` in `systemd-run`. `CapabilityBoundingSet=` is **not supported** in user-session `systemd-run` (exits 218); dangerous capabilities are instead denied via AppArmor `deny capability` rules.

See agent-isolation for the full model.

### Manifest Schema v1.1

Manifests gained an `isolation` block:

```yaml
isolation:
  unix_user: helm-platform
  apparmor_profile: helm-platform
  seccomp: default
  capabilities_drop: [NET_RAW, SYS_PTRACE, NET_ADMIN, SYS_ADMIN]
```

The `capabilities_drop` list is informational in v1.1 (enforced via AppArmor deny rules rather than systemd properties, due to the user-session limitation). `schema_version: "1.1"` added to distinguish from Phase 4 manifests.

### helm-launch v2

Key changes from v1:
- Manifest parsing delegated to root-owned `parse-manifest.py` (prevents profile name injection via manifest content)
- AppArmor profile allowlist validated before launch
- `AppArmorProfile=` and `NoNewPrivileges=yes` added to `systemd-run` properties
- `XDG_RUNTIME_DIR` and `DBUS_SESSION_BUS_ADDRESS` set explicitly for `sudo -u <agent-user>` sessions
- Per-agent NATS credentials read from `/home/<unix_user>/.helm/credentials/nats.env`
- `CapabilityBoundingSet=` removed (not supported in user systemd-run)
- Seccomp applied via `SystemCallFilter=@system-service` + explicit deny list

See helm-launch for full details.

### NATS: helm-health User + Credential Rotation

`helm-health` NATS user added with publish scope limited to `events.platform.{health,alerts}`.

Automated credential rotation added (`rotate-nats-creds.sh`, root-owned):
- Rotates `temporal-worker`, `platform`, `helm-health` passwords nightly (3 AM PM2 cron)
- **Does not rotate `helm-build`** — interactive sessions would break mid-session
- Regenerates `nats.conf` and hot-reloads via `SIGHUP`
- Per-agent files at `/home/<agent-user>/.helm/credentials/nats.env` updated atomically

See [nats.md](../components/agent/nats.md) for full details.

### Platform Health Agent

`platform-health-check.sh` runs every 5 minutes as `helm-health` via PM2 sudo wrapper. Queries Docker via a restricted socket proxy (TCP `127.0.0.1:2375`), publishes container health JSON to `events.platform.health` on NATS.

`helm-health` is intentionally **not** in the `docker` group — access is restricted to GET-only container listing via the socket proxy.

See platform-health.

### Graphiti MCP on Forge

Graphiti MCP server configured for the forge Claude Code environment, giving helm-build and platform agents access to the knowledge graph during sessions.

### Sudoers

`/etc/sudoers.d/helm-agent-launch` grants ted targeted `sudo` rights:
- Run `claude` as `helm-temporal`, `helm-platform`, `helm-health` (NOPASSWD, binary only)
- Run `rotate-nats-creds.sh` as root (NOPASSWD)
- Run `platform-health-check.sh` as `helm-health` (NOPASSWD, for PM2)

## Notable Gotchas

**`CapabilityBoundingSet=` not supported in user `systemd-run` (exit 218).** Capability restriction is handled entirely by AppArmor `deny capability` rules instead. This is functionally equivalent but the limitation is worth knowing — don't add `CapabilityBoundingSet=` to systemd properties in helm-launch.

**`/home/ted/` traverse bit.** Agent users need `o+x` on `/home/ted/` to traverse to any shared paths (e.g., `/home/ted/.claude/memory/shared/`). Set with `chmod o+x /home/ted`.

**PM2 sudo wrappers.** PM2 runs as `ted`. Cron jobs that must run as a different user (helm-health, root for rotation) require wrapper scripts that call `sudo -u <user> <script>`. Direct `exec_mode: fork` with `uid` in PM2 doesn't work reliably for user-session systemd targets.
